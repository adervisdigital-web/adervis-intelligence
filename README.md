# ADERVIS Intelligence — общая база (этап 2)

Та же система, что и локальная версия 0.3, но данные лежат на сервере: вы и Александр
работаете с одной базой с любого устройства. Кто что менял — видно в журнале.

## Файлы

```
index.html                     оболочка страницы
app.js                         весь интерфейс и обращения к базе
style.css                      оформление
theme.js                       тёмная/светлая тема до отрисовки
config.js                      адрес вашего проекта Supabase (заполняется один раз)
vendor/supabase.min.js         библиотека Supabase 2.110.0, та же, что в CRM
supabase/migrations/20260920_init.sql   таблицы, права доступа и журнал
```

## Настройка: семь шагов

Всё делается один раз и занимает минут двадцать.

### Шаг 1. Создать проект

1. Откройте https://supabase.com/dashboard и войдите тем же аккаунтом, что и для CRM.
2. Нажмите **New project**.
3. **Name**: `adervis-intelligence`.
4. **Database Password**: нажмите **Generate a password** и сразу сохраните его себе —
   второй раз его не покажут.
5. **Region**: выберите ближайший к России, например `Central EU (Frankfurt)`.
6. **Plan**: Free.
7. Нажмите **Create new project** и подождите около двух минут.

### Шаг 2. Создать таблицы

1. В левом меню проекта выберите **SQL Editor**.
2. Нажмите **New query**.
3. Откройте файл `supabase/migrations/20260920_init.sql`, скопируйте всё его
   содержимое и вставьте в окно запроса.
4. Нажмите **Run** (или Ctrl+Enter). Внизу должно появиться `Success`.

### Шаг 3. Выдать доступ

В том же **SQL Editor** выполните запрос, подставив реальный адрес почты
(строчными буквами):

```sql
insert into public.members (email, name) values
  ('ваша-почта@example.com', 'ADERVIS');
```

Кто не в этом списке — не увидит ни одной записи, даже если как-то заведёт аккаунт.

Сейчас вход общий на двоих. Имя из этой таблицы показывается в журнале
изменений. Чтобы разделить вход, добавьте вторую строку и второго пользователя
в шаге 4 — данные при этом менять не нужно.

### Шаг 4. Завести пользователя

1. Левое меню → **Authentication** → **Users**.
2. Кнопка **Add user** → **Create new user**.
3. Впишите тот же адрес почты, что и в шаге 3, и придумайте пароль.
4. Включите галочку **Auto Confirm User** — иначе вход не сработает до подтверждения почты.

### Шаг 5. Закрыть свободную регистрацию

1. Левое меню → **Authentication** → **Sign In / Providers** → **Email**.
2. Выключите **Allow new users to sign up** и сохраните.

Посторонние теперь не смогут даже создать аккаунт.

### Шаг 6. Подключить приложение к проекту

1. Левое меню → **Project Settings** → **API**.
2. Скопируйте **Project URL** и ключ **anon public**.
3. Вставьте их в файл `config.js`:

```js
window.INTEL_CONFIG = {
  supabaseUrl: 'https://ваш-проект.supabase.co',
  supabaseAnonKey: 'eyJ...'
};
```

Ключ `anon` публичный по замыслу Supabase: данные защищены правилами доступа внутри
базы, а не секретностью ключа. Его можно спокойно держать в репозитории.

### Шаг 7. Перенести данные из локальной версии

1. Откройте локальную версию 0.3 → **Настройки** → **Экспорт JSON**.
2. В общей базе войдите под своей почтой → **Настройки** → **Импорт JSON** → выберите файл.
3. Проверьте числа в окне подтверждения и нажмите **Перенести**.

Импорт добавляет записи и обновляет совпадающие по номеру. Ничего не удаляет,
поэтому его можно повторять без риска получить дубликаты.

## Этап 3: ИИ, который пишет черновики

Пять шагов, после которых в AI-рабочей зоне заработает кнопка «Написать черновики».

### Шаг 8. Вторая таблица

**SQL Editor** → **New query** → вставьте содержимое
`supabase/migrations/20260924_ai.sql` → **Run**. Это учёт обращений к модели:
он нужен для дневного лимита.

Затем так же выполните `supabase/migrations/20260924_service_grants.sql` —
он выдаёт права служебной роли. Без него серверная функция не сможет вести
учёт расходов, и дневной лимит работать не будет.

### Шаг 9. Ключ Gemini

1. Откройте https://aistudio.google.com/apikey
2. Нажмите **Create API key**, выберите проект Google.
3. Скопируйте ключ. Если у вас сохранён ключ от CRM — можно взять тот же.

### Шаг 10. Положить ключ в секреты проекта

1. В Supabase: **Project Settings** → **Edge Functions** → раздел **Secrets**.
2. **Add new secret**: имя `AI_API_KEY`, значение — ключ из шага 9.

Ключ лежит только здесь. В браузер он не передаётся, в репозитории его нет.

#### Смена AI-провайдера

Провайдер не зашит в код. Меняется теми же секретами, без правок и переустановки:

| Секрет | Зачем | По умолчанию |
|---|---|---|
| `AI_API_KEY` | ключ выбранного сервиса | — |
| `AI_PROVIDER` | `gemini` или `openai` (любой сервис с OpenAI-совместимым API) | `gemini` |
| `AI_MODEL` | название модели | `gemini-3.5-flash`, для `openai` — `deepseek-chat` |
| `AI_FALLBACK_MODEL` | запасная модель, если основная перегружена | `gemini-3.5-flash-lite` |
| `AI_BASE_URL` | адрес сервиса, если он не DeepSeek | адрес DeepSeek |

На бесплатном уровне Gemini модель иногда отвечает «перегружено» (503). Функция
сама повторяет запрос, а затем пробует запасную модель, и только потом
сообщает об ошибке. Какая модель в итоге написала текст — видно под формой
и в таблице `ai_usage`.

Примеры:

- **Gemini** — задать только `AI_API_KEY`.
- **DeepSeek** — `AI_PROVIDER=openai`, `AI_API_KEY=<ключ DeepSeek>`.
- **Российский шлюз с оплатой в рублях** — `AI_PROVIDER=openai`,
  `AI_BASE_URL=<адрес из личного кабинета>`, `AI_MODEL=<модель>`, `AI_API_KEY=<ключ>`.

После смены секрета функцию нужно опубликовать заново (или нажать Deploy),
чтобы она подхватила новое значение. В журнале расходов `ai_usage` видно,
каким провайдером и моделью сделан каждый запрос.

### Шаг 11. Опубликовать функцию

**Проще:** Supabase → **Edge Functions** → **Deploy a new function** → имя
`ai-write` → откройте файл `supabase/functions/ai-write/bundle.ts`, скопируйте
всё содержимое в редактор → **Deploy**.

**Через командную строку** (если удобнее): `supabase functions deploy ai-write`
из папки `intel`.

`bundle.ts` — это два файла функции, склеенные в один, чтобы их можно было
вставить в панель. Если правите `compose.ts` или `index.ts`, пересоберите:
`node tools/bundle.mjs`.

### Шаг 12. Проверить

Войдите в приложение → **AI-рабочая зона** → **Написать черновики**.
Через несколько секунд появятся варианты с указанием источников.

## Файлы в записях

Брендбук, фото и видео кейсов, документы прикладываются к записям базы знаний:
откройте запись → раздел **Файлы** → выберите файлы. До 50 МБ каждый.

- Хранилище закрытое: прямая ссылка без входа не работает. Приложение выдаёт
  временную ссылку на час и только вошедшему участнику.
- На карточке записи видно, сколько файлов приложено.
- Удаление записи удаляет и её файлы — об этом предупреждают заранее.
- Файлы не входят в выгрузку JSON: она о тексте базы. Для файлов резервная
  копия делается средствами Supabase.
- Бесплатный тариф Supabase даёт 1 ГБ хранилища.

Если проект создаётся заново, миграция `20260925_files.sql` заводит таблицу
вложений, закрытый ящик хранилища и правила доступа к нему.

## Что сделано для безопасности и расходов

- **Факты собирает сервер.** Приложение отправляет только задание: автора,
  площадку, направление и текст задачи. Список фактов функция берёт из базы
  сама и только публичные проверенные записи. Подменить страницу и вытащить
  внутренние сведения в запрос к модели нельзя.
- **Защита от команд внутри записей.** В запросе модели прямо сказано, что
  текст фактов — данные, а не инструкции.
- **Ссылки на источники.** У каждого черновика видно, на каких записях он
  держится. Выдуманные модель номера отбрасываются при разборе ответа.
- **Дневной лимит** — 30 запросов на человека. Счётчик ведёт сервер служебным
  ключом, из приложения его не подделать и не стереть.
- **Модель может ошибаться.** Черновик сохраняется в контент-студию со статусом
  «Черновик» — как заготовка для правки, а не готовый пост.

## Как это открыть

Файл нельзя просто открыть двойным щелчком: браузер запрещает такой странице
загружать соседние файлы. Нужен адрес. Либо публикация на GitHub Pages
(как у CRM), либо локальный запуск в папке проекта:

```
python -m http.server 8080
```

затем открыть http://localhost:8080

## Что защищает данные

- Правила доступа в самой базе: читать и писать может только почта из `members`.
  Ошибиться в интерфейсе и показать лишнее нельзя — проверка на сервере.
- Журнал изменений пишется триггерами базы. Из приложения его нельзя ни подделать,
  ни очистить.
- Одновременная правка одной записи двумя людьми не затирает чужой текст: тот, кто
  сохраняет вторым, получает предупреждение.
- В репозитории нет ни данных компании, ни паролей, ни секретных ключей.

## Проверено

- База данных: 26 проверок на настоящем Postgres — доступ, журнал, каскадное
  удаление замеров, ограничения значений, защита счётчика расходов на ИИ.
- Интерфейс: 42 проверки в Chromium — вход, разграничение доступа, создание,
  правка, удаление, конфликт правок, перенос данных, обрыв связи, телефон,
  генерация черновиков и дневной лимит.
- Сборка запроса к модели: 22 проверки — отбор фактов, запрет выдумок, разбор
  ответа и отсев ссылок на несуществующие записи.
